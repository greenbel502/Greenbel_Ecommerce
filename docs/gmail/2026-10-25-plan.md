# Gmail para consultas de contacto · propuesta concreta · 25/10/2026

La instrucción actual sustituye la pausa únicamente para las notificaciones de contacto y elige Gmail API. Financiamiento/OTP siguen pausados. Se conserva el formulario, su diseño, la RPC de registro, Supabase Auth y la autorización administrativa. DEV es el único destino autorizado de ejecución; producción se prepara y documenta, sin desplegar.

## Modelo propuesto para validar antes de la migración 028

1. `greenbel_private.gmail_connection`: una conexión por entorno/base, refresh token cifrado AES-256-GCM, remitente configurado, huella del cliente OAuth, permiso gmail.send, revisión UUID, fecha de conexión y estado connected/reconnect_required. Sin access tokens persistidos. Cifrado con clave privada del servidor y contexto de aplicación/cuenta; ni tokens ni ciphertext se serializan a clientes.
2. `greenbel_private.gmail_contact_notifications`: una fila única por `contact_messages.id`, estado pending/sending/sent/failed/unknown, número de intentos, UUID del intento, fecha y código de error controlado, identificador de mensaje Gmail y fecha de envío. Sin copiar datos personales innecesarios. FK a consulta y protección de concurrencia en las transiciones.
3. Ampliar la restricción del campo existente `contact_messages.notification_status` a esos estados más not_sent; no agregar campos ni cambiar el contenido de las consultas. Un trigger sobre INSERT crea la notificación únicamente para consultas nuevas cuando Gmail ya está conectado. Actualiza el estado de correo sin afectar el guardado de la consulta.
4. Tablas privadas, RLS/revocaciones y funciones de servicio accesibles exclusivamente al backend mediante service_role. El usuario público continúa usando solo `/api/contacto`; ningún visitante ni administrador desde Supabase cliente puede leer tokens o manipular estados de entrega.
5. Los registros históricos no se encolan, tampoco al conectar/reconectar Gmail. Conectar no envía mensajes acumulados. La RPC de registro y su cuota/idempotencia permanecen.
6. Una notificación tiene un único intento activo y no se vuelve a enviar si está sent. Los rechazos inequívocos permiten reintento administrativo, con límite y espera. Un timeout/corte/resultado incierto después de llamar a Gmail queda unknown, sin reintento automático: Gmail send no ofrece una clave de idempotencia que garantice entrega exactamente una vez. El administrador debe revisar su Gmail antes de resolver esa situación; no se promete una garantía inexistente.

## Implementación independiente que puede avanzar

- Biblioteca oficial googleapis, OAuth web server con scope exclusivo gmail.send, offline, consentimiento, PKCE, state/cookie HttpOnly SameSite=Lax (Secure en HTTPS), vínculo al mismo administrador y expiración de diez minutos.
- Rutas POST de conexión/reintento protegidas por administrador y origen; callback valida sesión/state antes de canjear código. Destinos fijos de redirección y errores sin secretos.
- Clave adicional `GMAIL_TOKEN_ENCRYPTION_KEY`, privada; no modifica las variables existentes ni activa correo de financiamiento. Variables de remitente/destinatario solo del servidor.
- Gmail envía MIME multipart texto/HTML escapado; From configurado y userId del remitente, Reply-To del cliente, destinatario exclusivamente de GMAIL_NOTIFICATION_EMAIL, referencia de consulta estable y Message-ID determinista. No se solicitan permisos de lectura.
- Tras confirmar persistencia, se programa la entrega del lado servidor sin convertir un fallo Gmail en fallo de registro. Panel Consultas incorpora únicamente conexión/estado/reintento necesarios y textos de estado coherentes. El formulario conserva su estructura y validaciones.
- Pruebas unitarias/HTTP y DEV controladas, autorización real por el administrador y correo real al destinatario configurado para comprobar recepción/Reply-To. No afirmar envío probado hasta recibir evidencia real. Configuración Vercel documentada; no cambios ni despliegue PROD.

Condición de aplicación: aprobación explícita de este modelo y migración 028 solo en DEV conforme a AGENTS.md. Ninguna migración se creará/aplicará antes de esa validación.
